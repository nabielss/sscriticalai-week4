  Semua label di bawah berlaku untuk fixture 100k baris, PG 16.15, satu writer berurutan, dan satu
  kali run per mode.

  1) Perbedaan mode transaksi dan autocommit

  Dibuktikan (RAN):

  - Mode transaksi: ADD COLUMN mengambil ACCESS EXCLUSIVE, dan lock itu dipegang sampai COMMIT (±1,03
  s). Dua INSERT kena LOCK_TIMEOUT, satu menunggu lalu gagal setelah commit, dan observer mencatat 8
  sampel dengan pemblokir pid migration.
  - Mode autocommit: 0 timeout dan 0 sampel lock. Tiga INSERT lolos selama UPDATE, sesuai harapan
  karena UPDATE hanya mengambil row lock.
  - Penyebab blokir: pembungkus transaksi memperpanjang lock ADD COLUMN dari 0,85 ms menjadi hampir
  seluruh migration. Pada skala ini, bukan CREATE INDEX atau CHECK yang tercatat sebagai pemblokir.
  - Rename merusak INSERT lama di kedua mode: 22 gagal di mode transaksi dan 20 di autocommit. Tidak
  ada jalan keluar lewat pemilihan mode.

  Belum dibuktikan:

  - Autocommit lebih aman. Tidak ada bukti untuk itu. CREATE INDEX biasa mengambil SHARE lock yang
  memblokir INSERT selama build. Percobaan 5 di autocommit selesai tepat setelah index selesai
  (33,5235 vs 33,519), jadi mungkin menunggu ±100 ms. Observer 0 sampel bisa berarti tidak menunggu
  atau terlewat. Tanpa durasi per percobaan, kedua kemungkinan itu tak terbedakan.
  - Perilaku di skala besar. Lama CREATE INDEX, CHECK (scan penuh di bawah ACCESS EXCLUSIVE), dan
  UPDATE belum diuji di 120M baris. Satu ukuran tidak memberi dasar menyebut hubungan linear.
  - Selisih antar mode. Jumlah sampel kecil (25 percobaan per mode, satu run). Mode transaksi
  dijalankan lebih dulu daripada autocommit, jadi cache bisa mempengaruhi. Lama migration hampir sama
  (1,07 s vs 1,05 s).
  - Mode yang dipakai runner production. Tidak diketahui.

  3) Dugaan currency pada INSERT yang terjadi saat UPDATE

  Dugaan: di mode autocommit, empat baris writer (id 200002–200005, semuanya country='DE') punya
  currency='USD', bukan EUR.

  Dasar (RAN dari hitungan, bukan dari nilai yang diamati):

  - UPDATE 100001 pada autocommit, padahal baris sesudah migration adalah 100005. UPDATE hanya
  menyentuh seed 100.000 ditambah satu baris writer yang lahir sebelum ADD COLUMN (percobaan 1). Empat
  baris sisanya tidak tersentuh.
  - Di Postgres READ COMMITTED, UPDATE memakai snapshot yang diambil saat statement mulai. Baris yang
  di-commit sesudahnya tidak terlihat olehnya.
  - INSERT lama tidak menyebut currency, jadi kolom itu terisi default 'USD' dari ADD COLUMN.
  - Di mode transaksi, UPDATE 100001 sama dengan jumlah baris akhir (100001), dan lock tabel mencegah
  celah itu. Tidak ada baris tertinggal di sana.

  Status: TIDAK TERVERIFIKASI. Yang teramati hanya hitungan baris. Nilai currency tidak diperiksa, dan
  databasenya sudah dibuang bersama container.

  Pemeriksaan yang akan memastikan:

  1. Setelah tiap mode, sebelum database hilang, jalankan dan catat:

     SELECT id, country, currency FROM invoices WHERE id > 200000 ORDER BY id;
     SELECT count(*) FROM invoices
     WHERE currency <> CASE country WHEN 'DE' THEN 'EUR' WHEN 'ID' THEN 'IDR' ELSE 'USD' END;

     Prediksi saya: autocommit menghasilkan 4 baris DE|USD (id 200002–200005) dan hitungan mismatch 4.
  Mode transaksi menghasilkan 0.

  2. Bandingkan dengan jumlah baris yang disentuh UPDATE (UPDATE n) untuk memastikan baris mana yang
  lolos dari snapshot.
  3. Repro deterministik, agar tidak bergantung pada waktu: sesi 1 menjalankan ADD COLUMN, lalu BEGIN;
  UPDATE … ; SELECT pg_sleep(2); COMMIT;. Sesi 2 meng-INSERT satu baris DE lama di tengah jeda itu.
  Setelah itu baca currency baris tersebut. Hasil USD memastikan mekanismenya.
  4. Dugaan ini salah jika keempat baris itu bernilai EUR. Dugaan itu juga tidak teruji kalau UPDATE
   ternyata menyentuh baris tersebut (hitungan UPDATE n tidak cocok).
